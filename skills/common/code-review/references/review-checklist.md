# 审查参考

只检查与当前改动相关的规则。以实际运行影响和项目标准为依据，下面的异味不构成自动违规。

## 需求与行为

- 每项已确认要求是否有实现和适当验证，是否增加未请求的外部行为。
- 默认值、返回结构、错误语义、权限、迁移和兼容性是否与契约一致。
- 测试是否覆盖真实调用路径；期望值是否来自独立依据，而非照抄实现。
- 失败是否明确暴露，临时兼容路径是否仍被引用，是否引入第二套规则或状态来源。

## 规范与代码异味

| 启发式 | 需要调查的信号 | 可考虑的方向 |
|---|---|---|
| 命名含糊 | 名称无法说明职责或数据含义 | 按实际领域含义命名 |
| 重复代码 | 同一业务判断在多处重复 | 在规则归属处集中维护 |
| 过度依赖他方数据 | 方法大量操作另一个模块的数据 | 调整职责位置，减少内部知识暴露 |
| 数据成组流转 | 相同字段反复作为一组传递 | 以有实际含义的类型或对象表达 |
| 基本类型承载过多语义 | 字符串等表示复杂领域概念且约束散落 | 显式表达其有效状态和规则 |
| 重复条件分派 | 多处对相同类型进行相同判断 | 统一分派规则，避免分支漂移 |
| 同一修改波及过广 | 一个行为变更要求多处同步修改 | 让同变职责聚合，但不机械合并文件 |
| 职责混杂 | 一个模块因多类无关原因反复变化 | 按变化原因划分边界 |
| 过早泛化 | 增加没有实际需求的扩展点或参数 | 保持当前需求所需的最小接口 |
| 长调用导航链 | 调用方必须知道深层对象结构 | 通过稳定接口表达所需能力 |
| 无收益转发层 | 抽象仅转发且未隔离依赖或规则 | 评估是否直接调用更清晰 |
| 不合适的继承 | 子类型忽略或否定大部分继承契约 | 考虑组合或调整共同契约 |

报告异味前确认其造成的维护或行为后果。项目明确采用的结构应按其上下文判断，不要仅凭命中表中关键词要求重构。
