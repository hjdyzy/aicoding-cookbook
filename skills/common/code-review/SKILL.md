# 代码审查

分别回答两个问题：改动是否符合项目规范，是否实现了用户要求。保持两条审查线的结论可辨认，避免“代码整洁”掩盖需求遗漏或错误行为。来源和本地适配记录见 [ORIGIN.md](ORIGIN.md)。

## 固定审查范围

先读取工作区状态和用户提供的提交、分支或 PR 信息：

- 分支或 PR：确认引用可解析，使用双方 merge-base 到目标提交的差异，记录准确的基线与目标。
- 指定提交区间：按用户指定的两个端点比较；审查单个提交时按其父提交比较，初始提交另行处理。
- 未提交改动：分别读取暂存区、未暂存差异和未跟踪文件清单，只读取与范围相关的新文件。
- 分支含未提交内容：按用户范围纳入或明确区分，不能只看 HEAD 就声称审完工作区。

用户未给基线时，先从 PR、分支跟踪关系和上下文判断；无法可靠推断时再澄清。无有效差异时直接报告范围为空。二进制、生成文件或无法读取的内容，明确说明实际覆盖情况。读取项目指令、贡献指南和相关编码标准；从更改位置追踪必要的调用链、配置及测试，不能仅凭一个差异片段断言缺陷。

完成标准：范围、基线、目标及未提交内容的处理方式明确，相关规范已定位。

## 确定需求依据

优先使用用户指定需求，其次查找当前对话的已确认范围、本地规格文件或提交关联的工单。项目已有 SPEC、验收标准或任务记录时直接引用。

没有完整规格时，依据用户已明确的要求、现有接口契约和调用行为审查；将缺少依据的需求项标为无法判断，不能当作需求审查通过。

完成标准：列出本次使用的需求依据，以及无法评估的部分。

## 两条审查线

**规范线**：对照项目规则检查错误处理、安全、边界、兼容、测试和可维护性。适用时读取 [references/review-checklist.md](references/review-checklist.md)。区分有明确出处的规则违反与需要判断的代码异味；项目约定优先于通用启发式，不要重复报告工具已经覆盖且未失败的纯格式问题。

**需求线**：逐项核对遗漏或部分实现、未请求的行为变化、实现与需求不符，以及测试看似通过却没有覆盖真实调用场景的问题。每项结论都应能关联到需求或契约。

环境允许且范围适合独立审查时，可拆分只读子任务，只提供准确范围、必要规范和需求，并说明使用了哪种方式。

完成标准：两条审查线均有结论或明确的证据缺口；发现的问题已结合相关代码核实。

## 验证与报告

报告每个有实质影响的问题：严重程度、当前文件和准确行号、触发条件、实际后果、证据依据及修复方向，并标注属于规范线、需求线或两者。相同根因合并为一项。整体按严重程度排列，保留每项的审查维度，避免同一缺陷重复计数。没有可证实的问题时明确说明，同时列出审查范围、验证结果及剩余盲区。

完成标准：报告的问题可定位、可解释、可采取行动；推测与已证实缺陷明确区分。
