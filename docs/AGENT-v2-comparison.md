## 已吸收的八项增量条款

| 优先级 | 上游条款 | 采纳前本地内容 | 已吸收的表述 |
|---|---|---|---|
| 高 | Bug-Fix Philosophy：根因修复、优先减法 | 已强调根因修复和清理废弃代码，但没有列出补丁反模式 | 修复前确认根因；优先移除冗余配置、失效分支和多余门禁，避免新增绕过路径或只消除表面报错 |
| 高 | Structural Fix Trigger：识别结构性问题 | 强调最小必要改动，缺少何时应统一修复的标准 | 涉及重复业务逻辑、多处事实来源、共享校验/权限/路由/缓存、状态同步或反复出现的同类故障时，先明确应保持的一致性约束，再在其归属模块统一修复 |

| 高 | Diff Review：交付前审查差异 | 当前要求测试，未明确最终 diff 检查清单 | 交付前检查重复逻辑、隐藏降级、宽泛异常捕获、废弃代码、未说明的行为变化、无效测试与安全回退，并修正明确问题 |
| 高 | Testing and Validation：按层验证并说明证据 | 已有测试、脚本验证和跨模块确认规则 | 在适用时依次做受影响单测、类型/静态检查、构建、最小冒烟；未执行的检查注明原因，不以服务已启动代替功能验证 |
| 中 | Planning：区分局部修复与结构性修复 | 已有里程碑及确认机制 | 非简单修复的计划包含根因、受影响文件、局部/结构性判断、方案和验证；最小补丁会增加不一致或债务时，明确比较长期修复方案 |
| 中 | Stop Rules：证据足够即结束 | 已要求简短，未定义调查结束条件 | 完成关键步骤后判断证据是否足以回答核心请求；达到验收标准后停止无关搜索和扩展 |
| 中 | Collaboration Style：低风险合理假设 | 当前有明确风险分级，但未说明一般歧义处理 | 不影响范围、验收或风险的缺失细节可以说明假设后推进；会改变范围或带来实质风险时再澄清；不得覆盖现有危险操作确认规则 |

落点对应：

- 工作模式：低风险合理假设。
- 代码开发规范：单一事实来源。
- 根因与结构性修复：根因优先、优先减法、结构性问题识别和改动范围。
- 计划纪律：局部/结构性修复判断及计划所需证据。
- 验证：分层验证、未验证项说明和交付前 diff 审查。
- 输出风格：证据足够且达到验收标准后结束。

## 按需采用（本次未纳入）

- **依赖注入与不可变优先**：对复杂业务逻辑有价值，但不要照搬“永不硬导入具体实现”或
  “绝不修改参数/全局状态”的绝对要求；小型运维脚本应保持直接、清晰和可测试。
- **并行代理职责划分**：只读探查、综合分析、主代理决策的职责可参考；仅在环境支持且任务
  明显受益时启用，写入必须划分所有权，不能将“默认并行”写成通用硬规则。
- **沟通风格**：自然、坦诚、少套话可以吸收；3–6 句、最多 5 点等数量限制不宜固定，
  应服从问题复杂度和用户要求。

## 已覆盖或不建议照搬

- 中文回复、先提示工具目的、短函数/浅嵌套、命名常量、最小改动、安全输入验证、
  禁止硬编码凭据、Debug-First、技能路由等，本地已有对应规则，无需重复堆叠。
- “机器配额充足，积极使用工具和代理”依赖个人环境，不能作为仓库通用约定。
- “后端单测硬超时 60 秒”宜改为可配置预算，保留本地已有的超时约定及超时原因说明。
- 上游通用开发规范不能替代本地运维条款：故障止血、回滚、变更窗口、灰度、权限回收、
  结构化操作记录、危险操作确认等应继续保留。
- 本次未新增 `AGENT-v2.md` 作为生效入口，推荐条款统一整合到现有 `AGENTS.md`，
  避免维护两份相互漂移的规则。
