# 故障诊断

把用户描述的具体症状变成可观察、可复查的判据，逐步缩小根因范围，再验证原始场景已恢复。来源和本地适配记录见 [ORIGIN.md](ORIGIN.md)。

## 确认现场与范围

先判断是否为生产故障、当前影响和用户已授权的操作范围。生产故障先按项目应急流程止血并留痕，稳定后再查根因。

以日志为主要证据，结合监控确定故障时间与影响范围，再关联近期代码、配置、部署和依赖变更。项目已有术语表或相关 ADR 时按需阅读。展示命令、日志或抓取产物前先脱敏；凭据通过环境变量或既有密钥机制传入，不写进复现脚本。

完成标准：明确原始症状、受影响范围、生产状态、已采取措施，以及尚缺哪些证据。

## 建立反馈闭环

优先找到一个实际执行过、能区分该故障是否发生的命令或操作。根据故障位置选择：

- 能触发真实调用路径的失败测试。
- 使用固定输入的 HTTP 请求、CLI 或浏览器操作。
- 对脱敏日志、请求或事件进行离线重放。
- 比较已知正常版本与异常版本的相同输入和输出。
- 间歇故障在隔离环境中重复触发，记录样本量、复现率及时间或随机种子。

判据应满足四项：已实际执行至少一次；走真实故障路径并断言用户的具体症状，故障存在时失败、修复后通过，不能仅断言“没有异常”或“进程能启动”；多次执行结论一致，间歇故障则有固定且足够高的复现率；单次耗时以秒计。为此缩短初始化和无关步骤，固定输入、时间、随机性与外部依赖。每次只删减一个输入、调用层或配置条件，重新执行，得到仍能暴露故障的最小场景。

无法复现时，列出已尝试的方式、现有证据和缺失条件；继续有价值的只读日志与代码调查，将推断明确标为未验证。不得伪造成功判据，也不得把缺少复现条件当作停止全部调查的理由。需要新增权限、生产探针或真实请求重放时，在该操作前按项目约定取得必要授权。

完成标准：记录原始场景、执行结果和明确的失败判据；若闭环尚未建立，明确其局限。

## 提出并验证假设

按证据解释力排序候选根因，每个假设写清：支持证据、可观察预测、能排除它的结果。假设数量由现有证据决定，不为凑数量增加猜测。必要时向用户简述排序，避免重复确认已知事实。

一次只改变一个变量或加入一个针对性探针。优先检查能区分候选原因的日志和运行状态；需要调试器、附加日志或性能剖析时，明确该操作验证哪个预测。临时探针加可检索的唯一标记；性能问题先建立相同负载下的测量基线，再比较延迟、吞吐或资源。假设不成立就更新结论，避免在失败补丁上继续叠加修改。

完成标准：每项已验证或已排除的假设都有证据；根因解释原始症状，而非仅解释附近的另一个错误。

## 修复与回归

先理解调用链，选择覆盖真实故障模式的公开接口或集成路径。能够自动化时，将最小复现变成修复前会失败的回归测试，再修改根因并观察通过。测试期望值来自需求、已知正常结果或独立推导，不复制被测实现。若现有接口无法覆盖真实故障，记录测试缺口和实际验证办法，避免编写无法捕获该问题的测试。

需要定位历史回归时先考虑隔离副本，避免改变用户当前工作区状态。修复后重跑最小复现和原始完整场景，按改动范围执行已有检查。

完成标准：原始症状已按同一判据验证恢复，相关检查通过；无法验证的部分单独列出。

## 收尾与输出

只清理本任务产生的临时探针和产物，保留已脱敏的定位证据；项目已有任务记录时更新其状态。

交付时说明：根因及证据、恢复或修复动作、实际执行的验证及结果、仍未验证的事项。未验证假设不能写成已确认根因；已止血也不等于根因已经修复。
